# Навыки агента

Этот файл описывает runtime-навыки приложения.
Подробные описания инструментов и их аргументов формируются из русских docstring и
аннотаций декорированных функций в `agents/tools/`. Схема БД здесь не дублируется: актуальный
блок генерируется из `storage/database.py` и добавляется в prompt отдельно.

## Извлечение полезных колонок

- Используется после загрузки файла или явного refresh, чтобы заполнить полезную S2T-таблицу приложения.
- Настройки берутся из `config/usefull_col_extraction.json`, `config/sheet_groups.json` и `config/column_mapping.json`.
- Не придумывай структуру результата: следуй конфигам и текущему состоянию загруженного файла.
- Если валидный план извлечения не получен, не записывай данные через молчаливый fallback; возвращай понятную ошибку.

## Сопоставление листов и колонок с конфигами

- Используется внутри извлечения полезных колонок.
- Для листов сначала выполняется точное и fuzzy-сопоставление с `config/sheet_groups.json`.
- Для колонок сначала выполняется точное и fuzzy-сопоставление с `column_mapping.json`.
- LLM вызывается только для тех листов или колонок, которые не удалось уверенно сопоставить локально.
- В LLM отправляй один лист за один запрос: имя листа, плоские названия колонок и примеры значений.
- Если self-check отклонил первый ответ LLM, передай модели причину отклонения без внутренних ID и разреши один корректирующий ответ; после повторного отклонения заверши extraction с явной ошибкой без fallback-записи.
- В LLM не отправляй внутренние идентификаторы, индексы, служебные роли и эвристические подсказки.
- Если LLM подтвердил новый полезный алиас, его можно добавить в текущий mapping-файл без дублей.

## Табличные запросы по S2T-трансформациям

- Используется, когда пользователь просит таблицу или строки S2T, маппинги, правила трансформации и обычные связи source → target.
- Источник фактов - сохраненная S2T-таблица приложения, а не старые catalog/mapping-таблицы.
- Для поиска идентификатора используй `search_s2t_transformations`.
- Для просмотра текущей таблицы используй `list_s2t_transformations`; после результата planner сам решает, достаточно ли данных для ответа.
- `list_s2t_transformations`, `search_s2t_transformations` и `summarize_s2t_tables` всегда работают со всей глобальной таблицей; не передавай им `file_id` и не фильтруй по нему через SQL.
- Отвечай компактно, по-русски, с указанием использованного инструмента или SQL-подхода.
- Если пользователь просит изменить данные из чата, объясни, что runtime chat-agent по умолчанию работает read-only.

## Сценарий: SQLite и `run_sql`

- Используй SQLite для точных фактов о файлах, листах, заголовках, исходных значениях Excel, описаниях и сохранённых строках `source_tables`, `target_tables` и `s2t_transformations`.
- Для фильтрации, подсчётов, агрегаций и произвольных табличных срезов используй `run_sql`.
- Для просмотра публичной DDL-схемы и проверки существования записей используй SQLite.
- Для готовых операций предпочитай узкие SQLite-tools: `list_files`, `list_sheets`, `list_file_sheet_headers`, `list_columns`, `search_s2t_transformations`, `list_s2t_transformations`, `summarize_s2t_tables` и `summarize_table_descriptions`.
- Не используй Cypher для чтения сырых Excel-строк, файловых описаний и точных табличных записей.

## Сценарий: Neo4j и `run_cypher`

- Neo4j содержит только узлы колонок `ETLColumn` и прямые рёбра `TRANSFORMS_TO`; сведения о файлах, листах, таблицах, строках и правилах получай из SQLite.
- Используй Neo4j для upstream/downstream lineage колонок, цепочек прохождения данных, поиска соседних колонок, путей и impact analysis.
- Для непосредственного lineage колонок одной таблицы предпочитай `trace_neo4j_lineage`.
- Для произвольного графового обхода или сложного графового среза используй `run_cypher`.
- Не используй SQL для многошагового обхода графа и поиска путей.

## Запросы по файлам, листам и заголовкам

- Используется, когда пользователь спрашивает, какие файлы загружены, какие листы найдены и какие заголовки распознаны.
- Для списка файлов используй `list_files`.
- Для листов используй `list_sheets` или `list_file_sheet_headers`.
- Для колонок конкретного листа используй `list_columns`.
- Не выдумывай имена файлов, листов, заголовков или ID; сначала получи их через tool или read-only SQL.

## Скилл: `s2t_loaded_data_summary_skill`

- Используется, когда пользователь просит краткое резюме, summary, описание или обзор по данным, которые появились после S2T-загрузки.
- Главный источник фактов — глобальная `s2t_transformations`; активный `file_id` к ней не применяй.
- Сам выбери подходящий read-only SQL и число вызовов `run_sql`, исходя из вопроса и уже полученных результатов.
- Итоговое резюме таблицы трансформаций должно отражать общий объём, направления source → target, представленные колонки и заполненность правил.
- Если данных нет, сообщи это прямо; не дополняй ответ выдуманными маппингами.

## Скилл: `s2t_table_summary_skill`

- Используется для суммаризации логических таблиц, представленных в `s2t_transformations`.
- В данных трансформаций различай логическую роль таблицы-приёмника и логическую роль таблицы-источника; одна строка описывает маппинг колонок между ними.
- Определи нужный уровень из запроса пользователя: таблицы-приёмники, таблицы-источники либо связи source → target.
- Для готовой агрегации по одной из ролей доступен `summarize_s2t_tables`; для иных разрезов доступен самостоятельно выбранный read-only SQL по `s2t_transformations`.
- Planner сам выбирает подходящий инструмент и параметры без файлового scope.
- Для каждой логической таблицы суммаризируй только подтверждённые данные: число представленных колонок, связанные таблицы другой роли, количество строк маппинга и наличие правил трансформации.
- Если полезно для ответа, добавляй характерные колонки или правила, но не подменяй суммаризацию выводом всех строк.
- Не смешивай логические ETL-таблицы источников и приёмников с физическими таблицами SQLite или именами Excel-листов.
- Идентификаторы логических таблиц в результатах анализа являются значениями S2T, а не `file_id`; файловые tools принимают числовой ID загрузки из UI или `resolve_file`.
- Ответ оформляй компактно по таблицам; пустые имена и отсутствующие правила отмечай как пробелы данных, а не восстанавливай предположениями.

## Скилл: `table_description_summary_skill`

- Используется, когда пользователь просит найти, объединить или кратко суммаризировать описания конкретной логической таблицы по её имени.
- Вызови `summarize_table_descriptions` с именем таблицы; при наличии UI-scope передай текущий `file_id`.
- Инструмент ищет точное имя без учёта регистра и внешних пробелов одновременно в `source_tables` и `target_tables`, объединяя результаты через `UNION ALL`.
- Одинаковые исходные записи не удаляй: каждое описание является отдельным фактом. Для итогового текста используй все элементы `combined_descriptions`.
- В финальном ответе сформируй одно краткое русское описание и укажи, в каких ролях найдена таблица: источник, приёмник или обе роли.
- Если совпадения есть, но описания пустые, сообщи об отсутствии описаний. Если совпадений нет, не ищи похожее имя эвристически и не придумывай описание.

## Публичная схема и хранилище

- Для вопросов про таблицы, DDL или схему используй сгенерированный блок `Актуальная схема SQLite`.
- Не поддерживай ручной список колонок в этом файле: источник правды - `storage/database.py`.
- По умолчанию показывай пользовательски значимые таблицы из сгенерированной схемы.
- Внутренние таблицы хранилища упоминай только при явном вопросе про устройство БД, debug или сырые значения.
- Старые catalog/lineage-сущности не используй и не предлагай как актуальный источник данных.

## Выбор подмножества полей в ответе

- Используется, когда пользователь просит показать не всю S2T-таблицу, а только часть полей.
- Выводи только запрошенные пользователем поля и не добавляй остальные для удобства.
- Если пользователь просит несуществующее поле, не угадывай: объясни, что оно недоступно, и предложи посмотреть актуальную схему.

## Саммаризация файла

- Используется для бизнес-саммари загруженного Excel-файла.
- Опирается только на сохраненные данные приложения и видимые фрагменты исходного файла.
- Пиши саммари по-русски: домен, назначение файла, ключевые сущности, видимые слои и заметные правила трансформации.
- Если LLM-provider недоступен или вернул ошибку, не придумывай саммари; возвращай понятную ошибку.

## Скилл: `file_description_skill`

- Используется, когда пользователь просит краткое описание, brief-summary или обновленное описание для загруженного Excel-файла.
- Основной источник правды - `files.description`. Если описание уже есть, переиспользуй его, а не генерируй заново без необходимости.
- Для чтения используй `get_file_description`: он возвращает только уже сохранённые `files.description` и `files.summary` без LLM-вызовов и без записи в БД.
- Если `files.description` пустое, сообщи об этом явно. При наличии `files.summary` можно опереться на него в ответе, но не генерируй и не сохраняй описание из read-only чата.
- Если пользователь явно просит сгенерировать, обновить, перезаписать или утвердить новое описание, используй `update_file_description` или `update_table_info_from_user_query` только по прямому запросу на мутацию.
- Ответ пиши по-русски коротко: домен, ключевые сущности, смысл данных и заметные правила, без мета-описания Excel-артефакта.

## Скилл: `table_info_update_skill`

- Используется, когда пользователь явно просит обновить сохраненную информацию о таблице по фактам из пользовательского запроса.
- Целевое хранилище - `files.description`.
- Строгая последовательность:
  1. Сначала убедись, что строка файла уже существует в таблице `files`.
  2. Затем убедись, что базовое описание уже сгенерировано и сохранено в `files.description`.
  3. Только после шагов 1-2 используй `update_table_info_from_user_query` или `update_file_description`.
- Никогда не обновляй сохраненную информацию до появления строки в `files`.
- Считай это узким мутационным путем, а не поведением обычного read-only чата.
