# Доменные навыки read-only chat-agent

Skills могут указывать, какие tools использовать и как выстраивать их
последовательность. Атомарные контракты tools — аргументы, ограничения, формат
результата и ошибки — задаются только descriptions и схемами самих tools.

## SQLite SQL

- Для выполнения произвольного read-only запроса по сохранённым данным используй
  `run_sql`.
- Для готовой операции предпочитай более узкий выбранный SQLite-tool, если он
  сразу возвращает нужный результат.
- SQLite хранит факты приложения, а не физические ETL-таблицы. Логические
  таблицы вида t_* представлены значениями source_table и target_table.
- Выполнение SQL и статический анализ его зависимостей являются разными
  операциями; если пользователь запросил оба результата, нужны оба шага.

## SQL lineage

- Для колонковых зависимостей SQL используй `parse_sql_column_lineage`, для
  зависимостей только таблиц — `parse_sql_table_lineage`.
- Если пользователь просит готовый граф SQL, сразу используй
  `visualize_sql_lineage`, без предварительного вызова обычного parser.
- При ссылке «этот запрос» или «эта трансформация» передавай полный SQL из
  истории, а не произвольно выбранную таблицу.
- Для Greenplum-синтаксиса применяй совместимый диалект SQLGlot.

## S2T-строки

- Для просмотра строк используй `list_s2t_transformations`, для поиска
  известного фрагмента — `search_s2t_transformations`.
- Для компактных списков, пересечений, объединений и разностей source/target
  используй `list_s2t_table_names`: эта готовая операция сама гарантирует
  корректную принадлежность имени одной или обеим ролям.
- `source_only` и `target_only` уже являются готовыми разностями множеств: не
  вычисляй противоположную роль вторым вызовом и не перепроверяй их через SQL.
- Для количества маппингов, полей и связанных таблиц по одной основной роли
  используй `summarize_s2t_tables`.
- Для произвольного среза или нестандартной агрегации используй `run_sql`.
- Для готового графа всех табличных связей используй
  `visualize_s2t_table_graph`, не вызывая перед ним невизуальные аналоги.
- s2t_transformations глобальна и никогда не ограничивается активным file_id.
- Одинаковые исходные строки являются отдельными фактами и не дедуплицируются.

## Путь S2T-преобразования

- Для объяснения последовательности S2T-правил и для просьбы показать этот путь
  схемой используй `trace_transformation_path`: он одним вызовом возвращает
  факты, `text_diagram`, Mermaid-код и рёбра.
- Downstream начинается с source_table/source_field, upstream — с
  target_table/target_field.
- В ответе каждый шаг всё равно показывай в физическом направлении потока:
  `source_table.source_field → target_table.target_field`; upstream меняет
  порядок обхода, но не разворачивает само ребро.
- Если tool вернул `text_diagram`, это готовая схема: перенеси её дословно и не
  добавляй собственную классификацию структуры пути.
- NULL, пустая строка и ровно «-» означают прямую трансформацию.
- Отсутствие подтверждения Neo4j не отменяет факты SQLite.

## Neo4j

- Для lineage известной колонки любой глубины используй
  `trace_neo4j_lineage`: он сам объединяет точные колонковые связи и правила
  wildcard `* → *`.
- Wildcard хранится как отдельный `ETLColumn` с именем `*` внутри конкретной
  таблицы; узлы разных таблиц имеют разные ключи. Конкретные колонки связаны с
  wildcard своей таблицы через `COVERED_BY`/`EXPANDS_TO`, а переход между
  таблицами сохраняет имя колонки.
- В ответе показывай каждое ребро в направлении `source → target`, даже если
  обход выполнялся upstream. Публичный шаг `* → *` означает перенос
  одноимённой запрошенной колонки через table-scoped wildcard, а не отсутствие
  маппинга и не смешивание произвольных колонок.
- Для непосредственного lineage таблиц используй
  `trace_neo4j_table_lineage`.
- Для произвольного графового обхода таблиц, нескольких условий, группировки
  или нестандартного среза используй `run_cypher`.
- Neo4j является синхронизированной проекцией: пустой графовый результат не
  доказывает отсутствие объекта или связи в SQLite.
- Колонковые узлы ETLColumn связаны TRANSFORMS_TO, табличные ETLTable —
  TABLE_TRANSFORMS_TO.

## Excel и описания

- Используется, когда пользователь спрашивает, какие файлы загружены, какие листы найдены и какие заголовки распознаны.
- Для каталога загрузок используй `list_files`, а точное имя файла разрешай
  через `resolve_file` перед файловыми tools.
- Для листов и заголовков используй `list_sheets`,
  `list_file_sheet_headers` и `list_columns` по требуемому уровню детализации.
- Для поиска значения используй `search_excel_values`; если нужен контекст всей
  строки, следующим шагом вызови `get_excel_row` с фактическими идентификаторами
  из результата поиска.
- Для смыслового поиска описаний используй `semantic_search_descriptions`, для
  точного имени логической таблицы — `summarize_table_descriptions`.
- Не выдумывай file_id, имена файлов, листов, колонок и таблиц.

## Скилл: `s2t_loaded_data_summary_skill`

- Используется, когда пользователь просит краткое резюме, summary, описание или обзор по данным, которые появились после S2T-загрузки.
- Главный источник фактов — глобальная `s2t_transformations`; активный `file_id` к ней не применяй.
- Сам выбери подходящий read-only SQL и число вызовов `run_sql`, исходя из вопроса и уже полученных результатов.
- Итоговое резюме таблицы трансформаций должно отражать общий объём, направления source → target, представленные колонки и заполненность правил.
- Если данных нет, сообщи это прямо; не дополняй ответ выдуманными маппингами.

## Скилл: `s2t_table_summary_skill`

- Используется для суммаризации логических таблиц, представленных в `s2t_transformations`.
- В данных трансформаций различай логическую роль таблицы-приёмника и логическую роль таблицы-источника; одна строка описывает маппинг колонок между ними.
- Определи нужный уровень из запроса пользователя: таблицы-приёмники, таблицы-источники либо связи source → target.
- Для готовой агрегации по одной из ролей доступен `summarize_s2t_tables`; для иных разрезов доступен самостоятельно выбранный read-only SQL по `s2t_transformations`.
- Planner сам выбирает подходящий инструмент и параметры без файлового scope.
- Для каждой логической таблицы суммаризируй только подтверждённые данные: число представленных колонок, связанные таблицы другой роли, количество строк маппинга и наличие правил трансформации.
- Если полезно для ответа, добавляй характерные колонки или правила, но не подменяй суммаризацию выводом всех строк.
- Не смешивай логические ETL-таблицы источников и приёмников с физическими таблицами SQLite или именами Excel-листов.
- Идентификаторы логических таблиц в результатах анализа являются значениями S2T, а не `file_id`; файловые tools принимают числовой ID загрузки из UI или `resolve_file`.
- Ответ оформляй компактно по таблицам; пустые имена и отсутствующие правила отмечай как пробелы данных, а не восстанавливай предположениями.

## Скилл: `table_description_summary_skill`

- Используется, когда пользователь просит найти, объединить или кратко суммаризировать описания конкретной логической таблицы по её имени.
- Вызови `summarize_table_descriptions` с именем таблицы; при наличии UI-scope передай текущий `file_id`.
- Инструмент ищет точное имя без учёта регистра и внешних пробелов одновременно в `source_tables` и `target_tables`, объединяя результаты через `UNION ALL`.
- Одинаковые исходные записи не удаляй: каждое описание является отдельным фактом. Для итогового текста используй все элементы `combined_descriptions`.
- В финальном ответе сформируй одно краткое русское описание и укажи, в каких ролях найдена таблица: источник, приёмник или обе роли.
- Если совпадения есть, но описания пустые, сообщи об отсутствии описаний. Если совпадений нет, не ищи похожее имя эвристически и не придумывай описание.

## Публичная схема и хранилище

- Для вопросов про таблицы, DDL или схему используй сгенерированный блок `Актуальная схема SQLite`.
- Не поддерживай ручной список колонок в этом файле: источник правды - `storage/database.py`.
- По умолчанию показывай пользовательски значимые таблицы из сгенерированной схемы.
- Внутренние таблицы хранилища упоминай только при явном вопросе про устройство БД, debug или сырые значения.
- Старые catalog/lineage-сущности не используй и не предлагай как актуальный источник данных.

## Выбор подмножества полей в ответе

- Используется, когда пользователь просит показать не всю S2T-таблицу, а только часть полей.
- Выводи только запрошенные пользователем поля и не добавляй остальные для удобства.
- Если пользователь просит несуществующее поле, не угадывай: объясни, что оно недоступно, и предложи посмотреть актуальную схему.

## Саммаризация файла

- Используется для бизнес-саммари загруженного Excel-файла.
- Опирается только на сохраненные данные приложения и видимые фрагменты исходного файла.
- Пиши саммари по-русски: домен, назначение файла, ключевые сущности, видимые слои и заметные правила трансформации.
- Если LLM-provider недоступен или вернул ошибку, не придумывай саммари; возвращай понятную ошибку.
