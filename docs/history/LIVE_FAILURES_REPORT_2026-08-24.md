# Подробный отчёт по провалам live-сценариев

> Исторический снимок. Актуальная оценка локальных моделей находится в
> [`CORE29_TOP2_FULL_REPORT.md`](../../CORE29_TOP2_FULL_REPORT.md).

Дата отчёта: 24 августа 2026 года.

## 1. Область отчёта

Отчёт составлен по уже сохранённым transcript, JUnit и comparison-артефактам.
Новых live-запусков для подготовки отчёта не выполнялось.

В отчёт входят:

1. Полный прогон от 23 августа 2026 года: 42 сценария, 23 passed,
   19 failed, один HTTP 500, 1097 LLM-вызовов, 246 tool calls и 4 275 528
   токенов.
2. Все повторные прогоны первых семи сценариев из Word-файла.
3. Две загрузочные проверки, дополняющие эти семь сценариев до первых девяти:
   сохранение всех сырых S2T-кортежей, включая пустой target, и подсчёт пустых
   target-колонок по листам.
4. Отдельные прогоны OpenRouter, GigaChat, Ollama и сценариев с Neo4j, если их
   сбой влиял на интерпретацию результата.

Важно: результаты полного прогона из 42 сценариев являются историческим
снимком до последних исправлений. После него целенаправленно стабилизировались
первые девять сценариев; остальные каталоговые сценарии целиком повторно не
запускались.

## 2. Краткий вывод

Основная масса ошибок находилась не в SQLite-данных и не в извлечении S2T, а на
границах между этапами агента:

- coordinator дробил одну аналитическую операцию на независимых workers;
- при materialize/dispatch терялись роли `source`/`target`, `table_name` и
  ограничение глобального S2T без `file_id`;
- router выбирал физический поиск в `data` или `run_sql` для анализа сохранённого
  SQL-текста;
- worker повторно искал уже полученный `transformation_rule` либо пытался
  исполнить логический ETL SQL в SQLite;
- observer оценивал последний вызов вместо накопленных доказательств и запускал
  лишние циклы;
- coordinate/aggregate иногда теряли обязательные литералы или возвращали
  транспортную JSON-обёртку;
- часть формальных провалов была вызвана не неверным ответом, а слишком жёстким
  тестом на формулировку, число вызовов или холодный старт модели.

Для первых девяти сценариев фактическая картина сейчас такая: семь сценариев
Word-файла в последнем полном прогоне дали 6/7; оставшийся сценарий затем вернул
правильные `mandatory_fields_count=1`,
`mandatory_fields_without_mapping_count=0` и пустой список. Его последний
формальный провал был ложным: тест дополнительно требовал слово `t_optn`, которого
не было в заданном шаблоне ответа. Эта лишняя проверка удалена. Обе загрузочные
проверки проходят. Единого нового live-прогона 9/9 после последней правки пока
нет.

## 4. Детальная история провалов первых девяти сценариев

### 4.1. Невалидный структурированный ответ coordinator

Наблюдение:

- `checks_source_and_target_type_compatibility` завершался HTTP 500 с ошибкой
  «Coordinator должен вернуть ровно один native call dispatch_worker»;
- `writes_s2t_test_protocol` завершался HTTP 500 с ошибкой невалидной структуры
  `submit_worker_plan`.

Первопричина: протокол plan/dispatch был описан текстом, но не был достаточно
жёстко обеспечен схемой вызова. Модель могла вернуть несколько native calls,
неполный объект или обычный текст.

Архитектурное исправление:

- каждый узел должен иметь единственный разрешённый structured tool;
- результат валидируется до изменения graph state;
- ошибка формата должна проходить ограниченный repair того же узла, не
  перезапускать весь supervisor;
- после исчерпания repair API должен возвращать диагностируемую ошибку этапа, а
  не безымянный HTTP 500.

Промпт:

> Верни ровно один native call разрешённого инструмента. Не добавляй текст до
> или после вызова. Каждый обязательный аргумент заполни из исходной task; не
> изменяй имена и роли сущностей.

### 4.2. Избыточная декомпозиция одной аналитической операции

Наблюдение:

- проверка риска дубликатов была разделена на четыре workers;
- получение expression и извлечение использованных полей выполнялось двумя
  workers;
- проверка типов делилась на отдельный worker типов и отдельный worker CAST,
  хотя оба факта нужны одному выводу;
- корректная проверка типов дошла до 33 LLM calls при лимите 32.

Первопричина: planner воспринимал каждый источник доказательств как отдельную
задачу, а не как несколько чтений внутри одной операции. Зависимый worker не
всегда получал факты предыдущего шага в пригодном для вычисления виде.

Архитектурное исправление:

- по умолчанию один пользовательский вывод должен соответствовать одному
  worker;
- отдельный worker нужен только когда результат шага становится новым входом
  следующей самостоятельной операции;
- dependency должен передаваться как typed result reference, а не как свободный
  пересказ модели;
- полные tool results следует хранить в result store; зависимому worker нужен
  read-only инструмент выборки/SQL по явно переданному result reference и его
  схеме.

Промпт coordinator:

> Несколько источников доказательств для одного вывода остаются одним шагом.
> Делить задачу можно только если следующий шаг невозможно сформулировать без
> фактического результата предыдущего.

### 4.3. Смешение файла, листа и логической ETL-таблицы

Наблюдение:

- `b3050000420005_paymentdetails` искался как имя Excel-листа;
- то же имя передавалось как `file_id`;
- `T_LOANSCONTRACT`, `t_optn` и `$$...` исполнялись как физические SQLite
  таблицы;
- при составлении протокола coordinator самопроизвольно переключался на
  `T_AGR_DEP`.

Первопричина: строковые идентификаторы не имели закреплённого типа сущности и
повторно интерпретировались каждым LLM-этапом.

Архитектурное исправление:

- формировать на входе coordinator неизменяемый generic task envelope с
  типизированными сущностями: `file`, `sheet`, `etl_table`, `column`, `sql_text`;
- роль `source`/`target` хранить рядом с сущностью, а не восстанавливать по
  формулировке на каждом этапе;
- перед tool call детерминированно проверять совместимость вида сущности с
  аргументом инструмента;
- не добавлять отдельные поля под каждый тест: достаточно общих `entities`,
  `constraints`, `required_output` и `evidence_requirements`.

Промпт:

> ETL table — значение в S2T, а не Excel sheet и не физическая SQLite-таблица.
> `file_id` может быть только явно указанным числовым идентификатором файла.
> Запрещено менять тип сущности или подставлять другое имя без результата tool.

### 4.4. Неверный домен данных для типов, SQL-признаков и S2T

Наблюдение:

- типы колонок искались в сырых строках `data`, из-за чего агент сообщал, что
  `uuid` неизвестен;
- сохранённый SQL пытались выполнить через `run_sql`;
- риск дубликатов отвергался из-за невозможности обратиться к `$$305stg`;
- SQL-признаки искались в физических строках, хотя задача требовала прочитать
  `GROUP BY`, `DISTINCT`, `JOIN`, `WHERE`, `CASE` и `COALESCE` из текста правила.

Первопричина: контракты инструментов описывали техническую возможность, но
недостаточно явно запрещали соседний неправильный домен.

Архитектурное исправление:

- capabilities инструментов должны содержать не только `use_when`, но и
  машинно проверяемые `input_domain`, `output_domain` и `forbidden_operations`;
- router должен выбирать необходимую полную палитру и проходить проверку
  покрытия задачи до запуска worker;
- полученный `transformation_rule` должен становиться фактом worker, а не новым
  поисковым запросом.

Уже внесённые контракты:

- `search_excel_values` — только сохранённые значения Excel-ячеек в `data`;
- `run_sql` — только публичные физические SQLite-таблицы;
- `transformation_rule` и SQL `$$...` не исполняются;
- признаки SQL анализируются по сохранённому тексту;
- точные S2T-роли обслуживает `list_s2t_transformations`.

### 4.5. Потеря роли и точного табличного scope

Наблюдение:

- запрос источника для `target_table=t_optn, target_field=optn_id` превращался
  в `source_table=t_optn, source_field=optn_id`;
- при поиске обязательных полей терялся `table_name=t_optn`, поэтому выбирались
  66 обязательных колонок всех таблиц файла;
- после защитного отказа planner пытался обойти его через
  `allow_all_tables=true`;
- глобальный S2T ошибочно ограничивался `file_id=3`;
- точные имена склеивались в `q` подстрочного поиска, который возвращал 0 строк.

Первопричина: task, planner, router и worker независимо восстанавливали фильтры
из текста; ни один слой не владел неизменяемым набором ограничений.

Архитектурное исправление:

- task envelope должен передавать точные role bindings без перефразирования;
- перед выполнением tool call нужен общий constraint checker: обязательный
  фильтр из task нельзя удалить, инвертировать или дополнить;
- общий `scope=all_tables` допустим только если исходная задача требует обе
  стороны либо не задаёт роль колонки;
- глобальные домены должны помечаться в schema metadata, чтобы worker не мог
  добавить файловый scope.

Промпт worker/observer:

> Сопоставляй target catalog только с `target_table`/`target_field`, source
> catalog — только с `source_table`/`source_field`. Каждый ролевой фильтр tool
> call должен присутствовать в task. Любой дополнительный ролевой фильтр —
> неподтверждённый и требует исправления.

Сейчас `scope` обязателен: `source_columns` и `target_columns` фиксируют роль,
`all_tables` явно объединяет обе стороны. Отдельный служебный
`allow_all_tables` удалён. Сохранность явно заданного `table_name` пока
обеспечивается контрактом; полноценная детерминированная проверка остаётся
архитектурной рекомендацией.

### 4.6. Observer зацикливался после получения достаточных фактов

Наблюдение:

- OpenRouter-прогон одного сценария занял 231 секунду, 21 LLM call и пять tool
  calls;
- observer однажды вернул Markdown `## Observation` вместо structured JSON;
- при корректном tool result fallback помечал результат неподтверждённым, после
  чего worker повторял поиск;
- в других прогонах observer требовал, чтобы последний результат один
  подтверждал всю составную задачу, не учитывая уже найденные факты.

Первопричина: observation была локальной к последнему вызову, а не
кумулятивной; parse failure смешивался с семантическим отрицанием результата.

Архитектурное исправление:

- хранить одну кумулятивную structured observation;
- различать `observation_parse_error`, `tool_error` и `goal_mismatch`;
- при `goal_satisfied=true` разрешать только finish, без новых data tools;
- при parse error повторять только observer, не tool;
- сохранять все ещё актуальные mismatches, удаляя только явно исправленные.

Это поведение уже в основном внесено: planner получает последнюю накопительную
observation, observer перечисляет все оставшиеся ошибки, а успешная observation
переводит worker в finish-only режим.

### 4.7. Потеря данных между workers и при финальной агрегации

Наблюдение:

- зависимый подсчёт вернул 236 различных source tables вместо значения для
  найденной `target_table`, потому что второй шаг потерял фильтр первого;
- сравнение двух витрин смешало доказательства: сначала заявило различие, затем
  утверждало, что обе используют `UNION ALL`, хотя для одной rules были названы
  отсутствующими;
- корректный ответ о риске дубликатов однажды вышел наружу как
  `{"coordinator_result": ...}`;
- OpenRouter нашёл правильное expression и source fields, но в финале потерял
  имя target field.

Первопричина: передавались краткие worker answers и ограниченные previews, а
связь результата с исходной задачей и точными идентификаторами восстанавливалась
LLM-пересказом.

Архитектурное исправление:

- хранить полный результат под непрозрачным result reference;
- передавать dependency как `result_ref + schema + required operation`;
- coordinate должен видеть исходную task, required output и structured
  observations, а не только prose workers;
- aggregate должен быть lossless transport: если coordinate уже выдал готовый
  ответ, не перефразировать его;
- одинаковая JSON-обёртка вокруг готового ответа должна сниматься
  детерминированно.

### 4.8. Ложные провалы тестов и смешение качества с производительностью

Наблюдение:

- простой правильный ответ «привет» занял 67,6 секунды и упал только по лимиту
  30 секунд;
- правильная проверка типов упала при 33 LLM calls против лимита 32;
- корректный ответ `mandatory_fields_count=1`,
  `mandatory_fields_without_mapping_count=0`, `[]` упал только потому, что в нём
  не было повторено `t_optn`;
- другой корректный JSON `1/0` упал из-за отсутствия ожидаемого текстового слова
  о маппинге;
- проверка дубликатов требовала Neo4j tool, хотя по уточнённому контракту задача
  должна найти сохранённую трансформацию и проанализировать SQL-текст.

Первопричина: один тест одновременно проверял семантику, конкретную
формулировку, маршрут и performance budget.

Архитектурное исправление тестовой системы:

- разделить `semantic correctness`, `routing contract`, `presentation` и
  `performance` на независимые assertions;
- правильный ответ не помечать бизнес-провалом из-за холодного старта или
  количества вызовов — это отдельная performance-регрессия;
- required tools проверять только когда выбор инструмента является частью
  публичного контракта, а не деталью реализации;
- для нестабильной локальной модели выполнять три повторения и отдельно считать
  pass rate, но не скрывать единичный неверный результат;
- для строгого формата проверять только явно запрошенные поля.

Для первых семи live-сценариев предел LLM calls повышен с 32 до 100. Это убирает
ложный функциональный провал, но не отменяет отдельную работу по сокращению
циклов.

## 6. Провайдеры и внешняя инфраструктура

Эти случаи нельзя считать ошибками S2T-логики, но они должны отражаться в
отчётности отдельно.

### OpenRouter

- Один прогон `catalog_04` занял 231,3 секунды, 21 LLM call и пять tool calls.
- Expression и source fields были найдены правильно, но target field исчез из
  финального ответа.
- Observer хотя бы один раз вернул Markdown вместо structured JSON, что вызвало
  повторение worker-цикла.
- Следующий прогон завершился `Tool-router вернул невалидный JSON-текст`.
- Ещё один повтор завершился `RateLimitError` на supervisor.

Рекомендация: capability probe structured output перед benchmark, отдельный
repair только для невалидного узла, provider-specific schema mode и отдельная
классификация rate limit. Нельзя повторять data tools из-за ошибки сериализации
observer.

### GigaChat-2-Max

Три фактических запуска завершились `ConnectError` уже на первом supervisor
вызове, без tool calls и токенов. Это недоступность транспорта/credentials, а не
ошибка промпта. Перед live suite нужен preflight: один короткий structured call,
проверка модели и доступного token quota. При провале suite должен помечаться
`provider unavailable`, а не `scenario failed`.

### Ollama

- Наблюдался `500 Internal Server Error` из-за отсутствующего
  `llama-server.exe`.
- Простой ответ мог занимать 67,6 секунды, что похоже на холодный запуск модели.

Рекомендация: preflight процесса и модели до pytest, один warm-up вне метрик,
раздельные `cold_start_seconds` и `agent_seconds`. Отсутствующий binary должен
останавливать suite до сценариев.

### Neo4j

До запуска Bolt часть сценариев не могла получить lineage. После появления
`Bolt enabled on localhost:7687` сценарии продолжились. Отдельно наблюдался цикл,
когда Neo4j уже вернул части результата, но observer требовал подтверждения всей
задачи последним ответом.

Рекомендация: health check Bolt и минимальный read query до suite; topology и
rules считать разными evidence types, а observer должен оценивать их
совокупность.

## 7. Рекомендуемая архитектура

### P0. Неизменяемый TaskEnvelope

Общие, не привязанные к тестам поля:

- `original_task` — исходная исполнимая задача без пересказа;
- `entities` — тип, значение и роль сущностей;
- `constraints` — точные scope/запреты/глобальность;
- `required_output` — требуемые факты или формат;
- `evidence_requirements` — какие классы доказательств нужны;
- `context` — только устойчивые правила, отдельно от задачи.

Каждый downstream-узел может добавлять найденные facts/result refs, но не менять
исходные entities и constraints.

### P0. Детерминированный audit tool calls

Перед выполнением вызова проверять:

- сохранены ли все обязательные фильтры task;
- не инвертированы ли source/target;
- не добавлен ли `file_id` в глобальный домен;
- не расширен ли table scope;
- соответствует ли тип сущности аргументу tool;
- не пытается ли `run_sql` исполнить сохранённый ETL SQL.

LLM observer после этого оценивает смысл результата, а не базовую корректность
аргументов.

### P0. Result store для зависимых вычислений

Полные tool results сохранять под непрозрачным reference вместе со schema.
Следующему worker передавать только нужные refs и разрешать read-only SQL по
явно выбранному сохранённому результату. Это предотвращает потерю фильтра и не
раздувает prompt полными данными.

### P1. Capability-based routing

Router выбирает одновременно необходимый набор tools, skills и schemas. Каждый
элемент может быть пустым, но worker всё равно выполняет минимум один внутренний
analysis tool для сохранения ToolMessage-цикла. Route проверяется на покрытие
evidence requirements. Контракты должны быть короткими, но содержать явный
`not_for`.

### P1. Кумулятивная observation и жёсткое завершение

Observation хранит все подтверждённые facts, все ещё актуальные mismatches,
limitations и result refs. При `goal_satisfied=true` worker может только
завершиться. Ошибка structured parsing повторяет observer, а не чтение данных.

### P1. Lossless coordinate/aggregate

Coordinate получает исходную task, required output и ordered structured worker
evidence. Aggregate не делает новый смысловой вывод; он только формирует
публичное представление. Готовый ответ, соответствующий output contract,
возвращается без перефразирования.

### P2. Наблюдаемость

В логах для каждого запуска сохранять:

- task конкретного worker;
- route attempt и выбранные tools/skills/schemas;
- реальные tool arguments;
- observation каждого цикла;
- причину reroute;
- coordinate result отдельно от aggregate result;
- result refs и schemas без копирования полных чувствительных данных;
- provider/transport errors отдельной категорией.

Большая часть этих данных уже появилась в текущей трассировке; важно сделать их
стабильной схемой, пригодной для автоматического diff двух прогонов.

## 8. Рекомендуемые изменения промптов

### Supervisor

> Сохрани все явно названные идентификаторы, роли и ограничения дословно. Не
> превращай ETL table в file или sheet. Task содержит текущее поручение, context
> — только устойчивые правила. Не добавляй фильтры и сущности из собственных
> предположений.

### Coordinator planner

> По умолчанию создай один шаг. Несколько tools или источников доказательств для
> одного вывода не являются причиной делить задачу. Новый шаг нужен только когда
> его вход зависит от неизвестного результата предыдущего шага.

### Dispatcher/materializer

> Копируй точные identifiers, роли, ограничения и required output из task. Не
> заменяй `target` на `source`, не добавляй `file_id` глобальному S2T и не
> расширяй табличный scope.

### Router

> Выбери необходимую палитру, достаточную для всех evidence requirements.
> Точный структурный фильтр использует list-tool; подстрока — search-tool;
> семантика — semantic search. Сохранённый SQL сначала получают из хранилища,
> затем анализируют как текст. Не выбирай physical data tools для логических ETL
> таблиц.

### Worker planner

> Используй исходную task, последний tool exchange и накопительную observation.
> Не повторяй уже подтверждённый поиск. При `goal_satisfied=true` заверши worker.
> Каждый tool call обязан сохранять все ограничения task.

### Observer

> Сравни совокупность подтверждённых фактов с task и required output. Перечисли
> все ещё не исправленные ошибки. Не объявляй 0 строк доказательством отсутствия,
> если вызов потерял фильтр, роль или домен. Не требуй повторно факт, уже
> подтверждённый предыдущим циклом.

### Coordinate

> Используй task и ordered evidence. Сохраняй точные идентификаторы и буквальные
> шаблоны ответа. Не объединяй несовместимые факты разных объектов; сначала
> составь симметричную evidence matrix, затем делай сравнение.

### Aggregate

> Если coordinator answer уже удовлетворяет required output, верни его без
> изменений. Не добавляй транспортную JSON-обёртку и не удаляй identifiers,
> числа, списки или оговорки.
